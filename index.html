01

使っているチャットツールで、必要な作業量が大きく変わります。ここを最初に確定させてください。

　SlackChatwork

02

処理の流れ

素直に「受け取ってから生成する」と作ると、必ず失敗します。理由は次の制約です。

設計を決めた制約Webhookは10秒で切られる

Chatwork の Webhook は10秒以内に応答しないと接続が切断され、しかも再送されません。資料生成は数十秒から数分かかります。受け取りと処理を分けないと、依頼が消えます。

03

ノウハウの持たせ方

ここが品質を決めます。原則は1つだけです。

原則元の資料を毎回読ませない。規則に圧縮して渡す

過去の提案書を数十ページ分そのまま読ませると、遅く・高く・精度も安定しません。抽出すべきものは、実際にはA4数枚に収まる規則です。一度だけ人が抽出して固定し、以降はその規則だけを渡します。

ノウハウ表の作り

分類見出し内容適用条件
共通結論から書く最初の3行で結論。理由と背景はその後に置く。（空欄）
共通数値の扱い推計値には必ず「推計」と付け、算出根拠を併記する。（空欄）
提案書価格の見せ方総額だけでなく、工程ごとの人日と単価を必ず併記する。提案書 見積 価格
議事録決定と宿題を分ける決まったことと、持ち帰りを別の見出しにする。担当と期限を必ず付ける。議事録 打合せ MTG

適用条件が空欄なら常に効きます。語句を書くと、その語が依頼文に含まれるときだけ効きます。関係のない規則を毎回送らずに済みます。

並べる順序に意味があります

順置くもの変わるか扱い
1役割の定義ほぼ不変キャッシュ対象
2共通ルールほぼ不変キャッシュ対象
3依頼に関係するルール依頼ごとに変わる対象外
4依頼文毎回変わる対象外

変わらないものを先頭に置くのが要点です。先頭から一致した部分だけがキャッシュに乗るため、順序を崩すと効かなくなります。

条件つきキャッシュが得になる回数

キャッシュには書き込み側にも課金があります。短い保持なら2回目、長い保持なら3回目の呼び出しから得になります。1日に数回しか動かない用途では、付けないほうが安く済みます。

04

構築の手順

上から順に進めてください。各段階に確認用の関数を用意してあるので、次へ進む前に必ず通してください。

  1. 入れ物を用意する

    スプレッドシートを1つ作ります。中のシートはコードが自動で作るので、空のままで構いません。生成物の保存先フォルダも作っておきます。

    それぞれのIDを控えます。URLの /d/ と /edit の間、フォルダは /folders/ の後ろです。

  2. Apps Script プロジェクトを作る

    既存のプロジェクトに足さず、新しく作ってください。他の自動化と関数名が衝突します。

    衝突する名前 
    getSheet_ / columnIndex_ / LOG_HEADERS / testEndToEnd_

  3. 鍵を保存する

    コードの中にAPIキーを書いたままにしないため、スクリプトプロパティへ移します。

    setupSecrets_() の中身 
    function setupSecrets_() {
  const p = PropertiesService.getScriptProperties();
  p.setProperty('ANTHROPIC_API_KEY', '');   // ← 生成AIのAPIキー
  p.setProperty('CHATWORK_TOKEN', '');      // ← チャット側のAPIトークン
  Logger.log('保存しました。コード内の値を消してから、もう一度保存してください。');
}

    実行したら、コード内の値を消して保存し直してください。

  4. 設定値を入れる

    書き換えるのは、環境によって変わる値だけです。

    置き換える箇所 
    SHEET_ID:       'スプレッドシートのID'
FOLDER_OUT:     '出力先フォルダのID'
ALLOWED_ROOMS:  ['反応させるルームID']   // ここに無いルームは無視します
TRIGGER_WORD:   '@bot'                  // 本文がこれで始まるときだけ動きます

  5. チャットへの投稿を確認する

    testChatwork_() を実行します。テスト用のルームに接続確認のメッセージが出れば成功です。

    ここで失敗する場合、原因はトークンかルームIDのどちらかです。生成AI側はまだ関係ありません。

  6. ノウハウの組み立てを確認する

    testKnowledge_() を実行します。見本の規則が3件入り、依頼文に応じてどれが選ばれたかがログに出ます。

    ここで「依頼に関係するルール」が空なら、適用条件の語句が依頼文と噛み合っていません。

  7. ウェブアプリとして公開し、Webhookを登録する

    デプロイ → 新しいデプロイ → 種類「ウェブアプリ」。アクセスできるユーザーは「全員」にします。チャット側のサーバーから叩かれるためです。

    発行されたURLを、チャット側の管理画面でWebhookとして登録します。

    URLの扱いに注意 
    Apps Script の受け口ではリクエストヘッダを取得できないため、
Webhookの署名検証ができません。

代わりに2段で守ります。
  1. ウェブアプリのURLを秘匿する（推測困難な文字列が実質の鍵）
  2. 本文の room_id を ALLOWED_ROOMS と照合し、一致しなければ無視する

署名検証が要件になる場合は、受け口を別基盤へ移してください。

  8. 定期実行を設置し、通しで確認する

    setupTrigger() で1分ごとの実行を設置します。同名のものは自動で消してから作り直すので、二重にはなりません。

    最後に testEndToEnd_() を実行します。受付表に1件積まれ、処理され、チャットへ投稿されるところまで通れば完成です。

05

先に知っておく制約

項目制約回避のしかた
Webhookの応答10秒以内。超えると切断され、再送もされない受け取りと処理を分ける（本構成）
署名検証Apps Script では不可（ヘッダを取得できない）URLの秘匿＋ルームIDの照合。要件が厳しければ別基盤へ
ファイル添付上限5MB超えるものはドライブに保存してリンクを投稿
投稿の頻度ルームごとに10秒あたり10回1回の処理件数を絞る（既定は3件）
API全体の頻度5分あたり300回同上
定期実行の間隔最短1分即時応答は望めない。受付の返事を先に出す
実行時間Apps Script の1回の実行に上限あり1回の処理件数を絞り、長い生成は分割する

運用ノウハウは放っておくと腐ります

数週間前に書いた規則が、もう存在しない体裁や担当を指していることがあります。定期的な棚卸しを運用に組み込んでください。更新日の列を設けてあるのはそのためです。月に一度、古い順に見直すだけで精度が保てます。
